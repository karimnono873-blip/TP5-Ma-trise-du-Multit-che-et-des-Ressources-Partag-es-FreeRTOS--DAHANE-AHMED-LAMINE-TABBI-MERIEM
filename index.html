1. Simulations & Architecture Logicielle

Observez la différence entre un code bloquant (Séquentiel) et un OS Temps Réel (Concurrent) pour faire clignoter 3 LEDs à des vitesses différentes[cite: 260, 261, 262, 263].

LED 1 (1000ms)
PA5 [cite: 261]

LED 2 (500ms)
PA6 [cite: 262]

LED 3 (400ms)
PA7 [cite: 263]

État du Système : Séquentiel (Bare Metal)

Durée de la boucle : 1000ms + 500ms + 400ms = 1900ms. Les LEDs sont bloquées les unes par les autres.

// SÉQUENTIEL (Mauvaise pratique pour la concurrence)
while(1) {
    HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5);
    HAL_Delay(1000); // Bloque tout le processeur

    HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_6);
    HAL_Delay(500);

    HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_7);
    HAL_Delay(400);
}

Deux tâches (A et B) de même priorité tentent d'écrire sur l'écran I2C en même temps sans protection[cite: 311, 312, 313].

Race Condition (Collision de données)

// TÂCHE A
void vTaskA(void *pvParameters) {
    for(;;) {
        lcd_print("SYSTEM OK "); // Est interrompue au milieu !
        vTaskDelay(10);
    }
}

// TÂCHE B
void vTaskB(void *pvParameters) {
    for(;;) {
        lcd_print("ALERTE !!"); // S'incruste dans le bus I2C
        vTaskDelay(10);
    }
}

Utilisation d'un Mutex (Mutual Exclusion). Lorsqu'une tâche possède la "clé" (Mutex), les autres tâches sont mises en pause jusqu'à ce que le bus I2C soit libéré[cite: 323, 324, 325, 326].

Accès Protégé (Synchronisation réussie)

SemaphoreHandle_t xMutexLCD;

void vTaskA(void *pvParameters) {
    for(;;) {
        // Demander la clé (Wait)
        if (xSemaphoreTake(xMutexLCD, portMAX_DELAY) == pdTRUE) {
            lcd_print("SYSTEM OK ");
            xSemaphoreGive(xMutexLCD); // Rendre la clé (Signal)
        }
        vTaskDelay(1000);
    }
}

2. Post-Lab : Ingénierie RTOS

1. Quelle est la durée totale d'un cycle complet de la boucle while(1) en approche séquentielle (Bare Metal) ?

Dans l'approche séquentielle, le processeur exécute chaque instruction l'une après l'autre de manière synchrone. Si nous avons trois délais bloquants successifs : 1000 ms, 500 ms et 400 ms[cite: 261, 262, 263].

La durée totale d'un cycle de boucle est la somme stricte de ces délais : 1000 + 500 + 400 = 1900 millisecondes (1.9 secondes)[cite: 266]. À cause de cela, la LED 1 ne clignotera pas toutes les secondes, mais changera d'état seulement toutes les 1.9 secondes.

2. Que fait le processeur pendant qu'une tâche est en vTaskDelay() ? Est-il bloqué ?

Contrairement à HAL_Delay() qui gèle le CPU dans une boucle infinie active (Busy-Wait), vTaskDelay() est une fonction non bloquante propre à FreeRTOS[cite: 289, 305].

Lorsqu'une tâche appelle cette fonction, le Scheduler (l'ordonnanceur) place cette tâche dans l'état "Blocked" et donne immédiatement le contrôle du CPU à une autre tâche qui est prête à s'exécuter. Si aucune tâche n'est prête, le processeur exécute la tâche "Idle" (qui peut être configurée pour mettre le microcontrôleur en veille et économiser la batterie)[cite: 306].

3. Si on modifie la priorité de la Task 1 à 2 (et on laisse les autres à 1), quel est l'impact si les tâches demandent le processeur en même temps ?

FreeRTOS utilise un ordonnancement préemptif basé sur les priorités. Le principe fondamental est : La tâche avec la plus haute priorité prête à s'exécuter obtient TOUJOURS le processeur[cite: 307].

Si la Tâche 1 passe en Priorité 2, dès qu'elle sort de son état vTaskDelay(), elle préemptera (interrompra) instantanément la Tâche 2 ou la Tâche 3 (Priorité 1) en plein milieu de leur exécution. Elle s'exécutera en priorité absolue, puis rendra le CPU aux tâches inférieures lorsqu'elle se remettra en pause.

4. Pourquoi voit-on des messages mélangés sur l'écran LCD lorsqu'on n'utilise pas de protection ?

Ce phénomène s'appelle une Race Condition (Condition de course) sur une ressource partagée[cite: 309, 317].

La fonction lcd_print() prend du temps pour envoyer chaque lettre via le bus I2C. Sans Mutex, la Tâche A commence à envoyer "SYS...". Soudain, le tick (l'horloge interne) de FreeRTOS retentit, le Scheduler met la Tâche A en pause et donne la main à la Tâche B. La Tâche B envoie "ALERTE". Résultat sur l'écran : une chaîne corrompue ("SYSALERTE...").

5. Dans quel cas choisirait-on une Queue (File) plutôt qu'un Mutex pour gérer l'affichage LCD ?

Un Mutex est utilisé uniquement pour la protection de ressource (verrouiller la porte de la pièce contenant le LCD)[cite: 319, 330].

Une Queue (File de messages) est utilisée pour la communication entre tâches. On choisirait une Queue si l'on voulait créer une architecture avec une tâche dédiée uniquement à l'affichage (Gatekeeper Task). Les autres tâches (Capteurs, Boutons) ne toucheraient jamais au LCD, elles se contenteraient d'envoyer leurs valeurs dans la Queue. La tâche d'affichage lirait la Queue une par une et mettrait l'écran à jour proprement, éliminant de fait tout besoin de Mutex.

6. Pourquoi la tâche vTaskLog ne consomme-t-elle aucune ressource CPU tant qu'on n'appuie pas sur le bouton (Sémaphore) ? Et que se passe-t-il si on oublie de faire un xSemaphoreGive() ?

Lorsqu'une tâche appelle xSemaphoreTake(..., portMAX_DELAY), elle passe dans l'état "Blocked"[cite: 336, 338]. Le Scheduler l'ignore complètement lors de l'attribution du temps processeur. Son utilisation CPU est de 0% jusqu'à ce que l'interruption matérielle du bouton donne le sémaphore (l'événement la réveille instantanément)[cite: 337].

Si l'on oublie d'appeler xSemaphoreGive() après avoir utilisé la ressource, la ressource reste verrouillée à jamais. Toutes les autres tâches qui attendent ce sémaphore ou ce mutex resteront bloquées indéfiniment. C'est ce qu'on appelle un Deadlock (Interblocage)[cite: 339].
